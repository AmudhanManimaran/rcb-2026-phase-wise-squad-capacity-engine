# EeSaala Tracker

**RCB Squad-Specific Phase-Wise Target Intelligence System · IPL 2026**

EeSaala Tracker calculates how many runs a specific Royal Challengers Bengaluru playing XI can score in each phase of a T20 innings, turns that capacity into a first-innings target and a checkpoint plan for overs 6, 16 and 20, tracks live deficits against the plan, and validates every prediction chronologically across RCB's 14 league matches. IPL Match 67 is the final validation case.

> **Data notice.** Player names reflect the RCB 2026 squad. Every performance value (player priors, matches, deliveries, results) is synthetic and generated by this project. Backtest metrics demonstrate the methodology on generated data; they do not measure real-world IPL predictive accuracy.

---

## 1. What the system does

| Question | Module | Output |
| --- | --- | --- |
| How much can this XI score in each phase? | Phase Capacity | Adjusted runs and expected wickets for Powerplay (1-6), Middle (7-16), Death (17-20) |
| What are realistic checkpoints? | Target Planner | Runs and wickets at overs 6, 16 and 20 |
| How do venue and opponent change them? | Capacity engine | Venue factor, phase share and opponent threat per phase |
| What target should RCB set batting first? | Target Planner | T_recommended = T_base x (2 - BSI) |
| Which phase should recover a shortfall? | Match Tracker | Deficit carry-forward across the remaining phases |
| How accurate are the predictions? | Backtesting | Walk-forward MAE, MAPE, bias, hit rate, failure classification |

It is not a win-probability model.

## 2. Technology

PostgreSQL 16 (SQL, PL/pgSQL, views, functions, triggers) · Python 3.11+ (FastAPI, Pandas, NumPy, Pydantic) · HTML5, CSS3, vanilla JavaScript · Chart.js 4 (bundled locally) · pgAdmin 4 for administration · Pytest.

The PPT specified Oracle + React + Recharts. The methodology, formulas and chronological logic are unchanged; only the implementation technology is adapted (see `docs/project_architecture.md`).

## 3. Quick start

### Prerequisites
- PostgreSQL 16 running locally (pgAdmin 4 optional)
- Python 3.11 or newer

### Steps

```bash
# 1. Install dependencies (a virtual environment is recommended)
python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

# 2. Configure the database connection
cp .env.example .env          # Windows: copy .env.example .env
# edit DB_USER / DB_PASSWORD to match your PostgreSQL installation

# 3. Build everything (about 30 seconds)
python -m backend.generator.data_loader

# 4. Start the API and dashboard
python -m uvicorn backend.main:app --reload
```

Open:
- Dashboard: <http://127.0.0.1:8000/> (redirects to `/app/index.html`)
- Swagger API docs: <http://127.0.0.1:8000/docs>

Step 3 creates the `eesaala_tracker` database, runs every schema file, loads the seeds, generates the synthetic season (CSV copies in `data/generated/`), loads it, runs the default backtest, calibrates parameters on the matches before Match 67, and re-runs the backtest with the fitted set. It is safe to run again; it rebuilds from scratch.

Optional: serve the frontend separately with `scripts/run_frontend.sh` (port 5500). The pages then call the API at `http://127.0.0.1:8000`.

### Run the tests

```bash
python -m pytest -v
```

Formula, solver and engine tests run without a database. API and backtesting tests run when the database is reachable.

### pgAdmin

The schema can also be built manually: run `database/schema/01_create_database.sql` against `postgres`, then 02 to 07 and the seeds (03, 01, 02, 04 order) against `eesaala_tracker`. The synthetic season itself is produced by the Python generator. Validation queries are in `database/validation/` (each returns zero rows when consistent) and reporting queries in `database/reports/`.

## 5. Frontend modules

1. **Dashboard** · season record, backtest KPIs, projected vs actual, Match 67 validation card
2. **Squad Intelligence** · all 25 players with pre-match phase SR and OutProb, cold-start flags, player drill-down
3. **Phase Capacity** · ball shares, team SR, venue factor, opponent threat, adjusted capacity for the match XI
4. **Target Planner** · recommended target, venue-shaped phase targets, DP checkpoint plan, custom XI and wicket-penalty controls
5. **Match Tracker** · live score input with deficit carry-forward, and an over-by-over replay of the actual innings against the pre-match plan
6. **Backtesting** · run backtest, calibrate, per-checkpoint errors, match-level results, parameter sets
7. **Analytics** · phase run rates, ball outcome mix, venues, opponent economy heat table, player contribution, bowling by phase

## 6. Key design decisions

- **No leakage.** Every prediction uses only matches completed strictly before the target match date (`SeasonData.history_before`). Tests verify this, including a test that rewrites future deliveries and checks the earlier prediction is unchanged.
- **Cold start.** Match 1 has no 2026 history, so profiles equal the synthetic priors. Formula 05 shrinks observed rates toward the prior with `k` pseudo-balls.
- **Two-layer engine.** The SQL layer (`06_functions.sql`) implements phase tagging, recency weights and weighted SR/OutProb; `validation/04_prediction_validation.sql` cross-checks the SQL results against the Python engine.
- **Out-of-sample validation.** Calibration uses matches 1-13 only. Match 67 is never used to fit parameters.
- **Validation case.** The generator fixes Match 67 as a bat-first fixture so all three checkpoints are observable.
- **Chase handling.** When a chase finishes before a checkpoint, that checkpoint is marked not evaluable and excluded from error metrics.
